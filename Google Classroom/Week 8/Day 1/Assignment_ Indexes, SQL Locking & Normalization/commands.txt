Q3
EXPLAIN ANALYZE 
SELECT * FROM academics.students WHERE dept_id = 1;

Seq Scan on students  (cost=0.00..1.12 rows=3 width=142) (actual time=0.015..0.018 rows=3 loops=1)
  Filter: (dept_id = 1)
Planning Time: 0.082 ms
Execution Time: 0.035 ms

Observation:
PostgreSQL picks a Seq Scan instead of an Index Scan even after creating the index on dept_id. This is because our students table has only a few rows, and scanning the table sequentially is faster and cheaper for the query planner than reading index blocks first.

b)
EXPLAIN ANALYZE
SELECT s.student_name AS full_name, e.grade
FROM academics.students s
JOIN academics.enrollments e ON s.student_id = e.student_id
WHERE e.grade = 'A+' AND s.dept_id = 2;

Observation:
The composite index on enrollments(grade, student_id) allows PostgreSQL to filter directly for rows where grade = 'A+' and join on student_id without scanning unrelated enrollment rows. On larger tables, this improves performance by avoiding full table scans.

Q5
BEGIN;

SELECT * FROM academics.students 
WHERE student_id = 1 
FOR UPDATE;

UPDATE academics.students 
SET cgpa = 8.95 
WHERE student_id = 1;

COMMIT;

Explanation:
If another session tries to run an UPDATE or SELECT FOR UPDATE on student_id = 1 while this transaction is still open, it will pause and wait. It stays blocked until the first transaction completes with COMMIT or ROLLBACK.

Q6
Session A:
BEGIN;
SELECT * FROM academics.students WHERE student_id = 1 FOR UPDATE;

Session B:
UPDATE academics.students SET cgpa = 9.10 WHERE student_id = 1;

Session A:
COMMIT;

Observation:
When running the update in Session B, the command did not execute immediately—it stayed in a waiting state because Session A held an exclusive lock on that row. The moment Session A ran COMMIT, Session B immediately unblocked and finished its update.

Q7
A deadlock happens when two transactions are waiting on each other to release a lock, so neither one can continue. For example, Transaction 1 locks student 1 and waits for student 2, while Transaction 2 locks student 2 and waits for student 1. When PostgreSQL detects this circular wait, it automatically aborts one of the transactions with a deadlock error so the other one can finish. The best way to prevent deadlocks in application code is to always update rows and tables in the exact same order across all queries.

Q9
In the enrollments table, the primary key is the composite key (student_id, course_id). Adding student_full_name violates 2NF because student_full_name depends only on student_id, not on the entire composite key. This is a partial dependency. Instead, the student name should be stored only once in the students table and referenced in enrollments using the student_id foreign key.

Q11
Adding enroll_count to courses is denormalization because the value is already derivable by counting rows in the enrollments table, so it introduces redundant data. The read benefit is that queries showing course catalogs can display the total enrolled students instantly with a simple SELECT, without needing an expensive COUNT() join across thousands of enrollment records. The risk is data inconsistency: if the trigger is disabled, fails, or someone bypasses it during bulk updates, enroll_count will become incorrect and out of sync with actual data.
